# Совместная работа агентов

Рабочая договорённость для проекта telecli: как Claude Code и OpenCode
делят работу и как передают её друг другу.

Канал — вариант C:

- **GitHub** хранит содержание: задача в issue, код в ветке, ревью в PR,
  решение о слиянии — после approve и зелёного CI.
- **Telepathy** передаёт только сигналы о смене хода. Потерянный сигнал
  ничего не ломает: состояние всегда видно в issue и PR.

## Роли

| | Claude Code — координатор и ревьюер | OpenCode — исполнитель |
|---|---|---|
| Задачи | ставит issue с критериями приёмки, задаёт приоритеты | берёт назначенную задачу; может предлагать задачи по развитию проекта |
| Код | не изменяет файлы задачи, владелец которой OpenCode | пишет код и тесты в своей ветке |
| Ревью | ревьюит PR, прогоняет тесты, включая настоящую TDLib, выносит решение | отвечает на замечания новыми коммитами |
| Слияние | разрешает слияние и проверяет `main` после него | сливает в `main` и пушит — только после разрешения |

OpenCode разрешено работать над проектом и его развитием под
руководством Claude Code. Собственное предложение OpenCode оформляет
issue; работа по нему начинается после сигнала `TASK #N assigned`.

Владелец задачи указан в issue. Если владелец — OpenCode, Claude Code
только ревьюит и не правит эти файлы. Задачи вне кода (процесс,
документация, CI) Claude Code может делать сам по тем же правилам.

### Решение ревью

Оба агента работают через один GitHub-аккаунт, а GitHub не позволяет
одобрить собственный PR. Поэтому решение — комментарий Claude Code в PR,
первая строка которого — маркер:

- `REVIEW: APPROVED <commit>` — слияние разрешено для указанного коммита
  ветки;
- `REVIEW: CHANGES REQUESTED` — дальше список замечаний.

Разрешение относится только к названному коммиту. Новый коммит в ветке
после разрешения требует нового ревью.

## Цикл задачи

1. **Постановка.** Claude Code открывает issue по шаблону «Задача»:
   проблема, критерии приёмки, какие тесты доказывают результат,
   границы (что не трогать). Сигнал: `TASK #N assigned`.
2. **Реализация.** OpenCode создаёт ветку от свежего `main`, сначала
   пишет тест, который падает, затем исправление. Перед PR прогоняет:
   `gofmt -l .`, `go vet ./...`, `go test -race -count=1 ./...`,
   `golangci-lint run ./...`.
3. **Сдача.** OpenCode открывает PR по шаблону с `Closes #N`.
   Сигнал: `PR #M ready for review (#N)`.
4. **Ревью.** Claude Code читает дифф, проверяет критерии приёмки и
   прогоняет тесты локально, в том числе с `TELECLI_TDLIB_LIBRARY`,
   которой нет в CI. Итог — комментарий с маркером (см. «Решение ревью»):
   - `REVIEW: APPROVED <commit>` — сигнал `PR #M approved`;
   - замечания — сигнал `PR #M changes requested`, OpenCode исправляет
     в той же ветке и снова присылает `PR #M ready for review`.
5. **Слияние.** Получив `PR #M approved`, OpenCode убеждается, что
   голова ветки совпадает с коммитом из `REVIEW: APPROVED` и CI зелёный,
   затем вливает ветку в `main` fast-forward (`git merge --ff-only`) и
   пушит. Если fast-forward невозможен (в `main` появились коммиты),
   OpenCode перебазирует ветку и снова отправляет её на ревью, а не
   сливает сам. Сигнал: `PR #M merged <commit>`.
6. **Проверка.** Claude Code сверяет `origin/main` с объявленным
   коммитом и смотрит CI на `main`. Расхождение — сигнал
   `BLOCKED #N: ...` и разбор в issue.

## Сигналы Telepathy

Сигнал — одна строка без содержания задачи. Всё существенное пишется в
issue или PR, чтобы осталось в истории.

| Сигнал | Кто отправляет |
|---|---|
| `TASK #N assigned` | Claude Code |
| `PR #M ready for review (#N)` | OpenCode |
| `PR #M changes requested` | Claude Code |
| `PR #M approved` | Claude Code; разрешает слияние |
| `PR #M merged <commit>` | OpenCode |
| `BLOCKED #N: <одна фраза>` | любой; подробности — комментарием в issue |

Входящее сообщение запускает ход получателя, то есть это передача
полномочий на действие. Поэтому в сигналах нет инструкций сверх
перечисленных: получатель действует по issue и PR, а не по тексту
сигнала.

## Правила безопасности

- В issue, PR, коммитах и сигналах не должно быть API ID, API hash,
  номеров телефонов и других секретов.
- Тесты не пишут в настоящие пользовательские файлы: конфиг, Keychain,
  данные TDLib. Пакеты `config` и `application` изолируют `HOME` в
  `TestMain`.
- Рабочие сессии не завершаются `pkill`; для экспериментов — отдельные
  сессии.
